## Honest status

ChakTech is an online store for tech and electronics in Tunisia that I built as
a full-stack developer for a client. The store is live on its own domain after a
cutover from WordPress and WooCommerce in early October 2026.

It was built with an AI-assisted workflow that I directed, so I do not call it
hand-written or solo. I have no measured order, revenue, traffic or page-speed
figure to show, so this page does not invent any. Checkout is cash on delivery
only, which is how most Tunisian online orders still work. Other payment methods
exist in the code only as disabled placeholders.

## Hard problems

<DecisionCard
  title="Leaving WordPress without losing the catalog"
  subtitle="Migration with a no-price-no-sale rule"
  problem="A store with a large WooCommerce catalog needed to move to a custom stack without publishing broken products or losing history."
  decision="An import pipeline reads the WordPress database dump into PostgreSQL, a reconciliation script compares it with the result, and a read-only audit compared the final dump with the live database at cutover. A rule that no product can be sold without a price is enforced in four places: the schema, order creation, the importer and the storefront."
  result="The admin has been the source of truth since the early October cutover. A later fix made a variable product's parent price the cheapest purchasable variation."
/>

<DecisionCard
  title="Tenant isolation on a shared API"
  subtitle="Host resolution plus a token-pinned tenant"
  problem="The admin always calls one API host, so the hostname alone cannot say which store a signed-in user belongs to."
  decision="Anonymous storefront traffic resolves its store from the hostname and fails closed with a 421 on an unknown host. Signed-in traffic is pinned to the tenant in the token and cross-checked against the host. The tenant is never read from a client-supplied header."
  result="20 test files cover tenant isolation across carts, orders, cache, search and email. The product was designed tenant-scoped and launched as a single store, so I do not call it a multi-client SaaS."
/>

<DecisionCard
  title="Order integrity and reliable order email"
  subtitle="The server is the authority"
  problem="Prices, stock and totals must come from the server, orders must survive retries and races, and a failed email must not lose or duplicate an order."
  decision="Order pricing and stock are resolved server-side and client totals are ignored. Orders use an idempotency key and row locks. A transactional outbox sends the order emails, with per-recipient idempotency so a retry does not resend the customer confirmation when only the internal leg failed."
  result="Outbox recovery was observed working after a production reliability batch in early October. This is the engineering result, not a business figure."
/>

## System Design Notes

<Callout variant="info" title="Verified technology stack">
  Three independent repositories. Storefront: Next.js 16, React 19, next-intl with French, Arabic (right to left) and English, Redux Toolkit. Admin: Next.js 16 with Payload CMS 3 and its multi-tenant plugin. API: Express and TypeScript on PostgreSQL through Drizzle, with Redis, BullMQ, Typesense search, Cloudflare R2 media, Sentry and PostHog. Shipped as Docker containers on Dokploy behind Traefik and Cloudflare.
</Callout>

<DecisionCard
  title="Search and caching"
  subtitle="Typesense plus a Redis cache with stampede protection"
  problem="Product discovery needs to be fast and typo tolerant, and cached pages must not go stale when a price changes."
  decision="Typesense serves search and faceting, fed by an outbox and a periodic reconciliation job. Redis caching has stampede protection, and a tagged revalidation endpoint refreshes storefront pages when catalog data changes."
  result="Search indexing and cache invalidation are driven by the same events that change the data, not by manual steps."
/>

<DecisionCard
  title="Operability"
  subtitle="Readiness, graceful shutdown and backups"
  problem="A store that takes orders must restart and recover without losing work."
  decision="Readiness and health endpoints, a leader-gated job scheduler, a graceful drain on shutdown, a dedicated backup worker, and Sentry and PostHog for errors and tracing."
  result="Restores are not claimed as proven in production: a restore drill is an open item below."
/>

## What I would take from this

A migration is finished when the old system can be switched off, not when the
data has moved. Make the server the authority for money and stock. And label what
is merged, what is released, and what is only planned.
