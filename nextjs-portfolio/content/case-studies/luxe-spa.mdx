## Honest status

Luxe is a white-label booking and CRM platform I built, solo, for a client. One
client deployment is live. It is **not** a multi-tenant SaaS: each client gets its
own database, and tenant isolation was designed but deliberately not built.

I have no measured booking volume, revenue or no-show reduction to show, so this
page does not invent any. What I can show is the engineering: how double bookings
are prevented, how the work was dated and tested, and what a real self-audit found.

## The hard problem

A booking page can look perfect and still let two people book the same specialist
at the same minute. The fix cannot live in the interface. The browser asks for a
slot and the server decides.

<DecisionCard
  title="Double-booking prevention"
  subtitle="Enforced in the database, not the UI"
  problem="Two customers (or a customer and a receptionist) request overlapping time for the same specialist or the same chair, at the same moment."
  decision="A PostgreSQL EXCLUDE USING gist constraint rejects overlapping time ranges per specialist, including buffer time, and a second one rejects double-allocating a physical resource. Booking creation runs in a Serializable transaction with the slot re-checked inside it, and an Idempotency-Key makes retries safe."
  result="A documented race test on 2026-10-02 against real PostgreSQL: two concurrent requests for one slot gave one winner, a 409 for the loser, and no orphan rows or leaked database errors. No production load result is claimed."
/>

The path to that design is visible in the migrations: a unique index on active
slots first (26 July), replaced the next day by the exclusion constraint, then
extended to buffers and resources (11 August). Finding a real race before launch,
rather than after, is the part I would repeat.

## System Design Notes

<Callout variant="info" title="Verified technology stack">
  Two independent repositories. Frontend: Next.js 16, React 19, TypeScript, Tailwind CSS 4, next-intl (English, Spanish, Vietnamese), TanStack Query, Radix UI. Backend: Express 5, PostgreSQL with Prisma, Zod, Redis with BullMQ, ImageKit. Per-client work lives on one branch per client, on top of one product branch.
</Callout>

<DecisionCard
  title="Availability engine"
  subtitle="Server-authoritative scheduling"
  problem="Showing slots that are really bookable, across opening hours, staff shifts, date overrides, which specialist can do which service, buffers, shared resources and time zones."
  decision="One availability service computes slots from opening windows, shifts, overrides, qualifications, per-service buffers, resource requirements and the location time zone, including multi-service sequences and 'any available specialist'. The interface only renders what the server returns."
  result="The same rules decide what is shown and what is accepted, so the page cannot offer a slot the server would refuse."
/>

<DecisionCard
  title="Non-blocking notification pipeline"
  subtitle="Queue-backed workers"
  problem="Provider-dependent messaging and follow-up work must not block or break the booking request."
  decision="Notification, review, SMS, media and import jobs run on BullMQ workers with Redis. A durable delivery record is written before a job is queued, and jobs use deduplicated ids and exponential-backoff retries."
  result="Provider work stays out of the request path. Delivery success in production is not claimed without receipts."
/>

<DecisionCard
  title="Per-client configuration without forking the product"
  subtitle="Config fallback plus database settings"
  problem="Different salons need their own brand, catalog, wording and settings without maintaining a separate codebase each."
  decision="A static site configuration is the fallback, database site settings override it, and CSS variables carry the brand. A client's data arrives through forward migrations, not hand edits."
  result="A branded client deployment on top of one product. Runtime multi-tenant isolation is not claimed: each client has its own database."
/>

The admin inbox is near-real-time: it polls every 5 to 10 seconds while a tab is
open, backed by an inbox service. It does not use WebSockets.

## What I would take from this

Treat the database as the authority for anything two people can race on. Audit
your own work before a client does. And publish the gates, not the adjectives.
