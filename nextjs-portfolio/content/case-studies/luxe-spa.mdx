## System Design Notes

To support reusable white-label client deployments while maintaining clear runtime boundaries, the Luxe Spa platform was architected around three critical backend subsystems: dynamic configuration, booking synchronization, and an asynchronous background worker pipeline.

<Callout variant="info" title="Verified Technology Stack">
  The system is built with Next.js 16 App Router, React 19, Tailwind CSS 4, Zustand, Express.js/TypeScript, PostgreSQL + Prisma ORM, Socket.io, Redis/BullMQ, ImageKit CDN, and Zod validation.
</Callout>

<DecisionCard
  title="Vertical Adaptability"
  subtitle="Dynamic Preset Engine"
  problem="Adapting the booking platform to different service domains without maintaining separate product implementations."
  decision="The repository contains centralized preset/configuration paths that populate catalog and site-setting records for a service vertical."
  result="Provides a reusable configuration boundary for client-specific terminology, catalog, branding, and operating settings; runtime tenant isolation is not claimed here."
/>

<DecisionCard
  title="Slot Concurrency & Real-Time Sync"
  subtitle="Transactional Booking Layer"
  problem="Preventing stale-slot and conflict errors when multiple customers or staff users request overlapping appointment times."
  decision="Implemented server-side slot validation at booking time with Prisma transaction boundaries and Socket.io/inbox code paths for operational updates."
  result="The code protects booking creation with current-state validation and conflict handling; a production concurrency load result is not claimed here."
/>

<DecisionCard
  title="Non-Blocking Notification Pipeline"
  subtitle="Offloaded Async Workers"
  problem="Preventing provider-dependent messaging and follow-up tasks from blocking the main API request path."
  decision="Offloaded notification, review, SMS, media, and import work to BullMQ workers backed by Redis, with durable notification state for retries and provider errors."
  result="Keeps provider-dependent work outside the main request path; provider delivery success and completion guarantees are not claimed without live receipts."
/>
