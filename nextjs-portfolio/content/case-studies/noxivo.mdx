## Honest status

Noxivo is my own multi-tenant WhatsApp automation platform for agencies. It is in development and not open to the public: the public site is a waitlist page, and the docs site is online. I built and maintain it with AI coding agents. It has no verified customers, tenants, messages or revenue, and its own launch gate still reads "not ready".

The git history starts on 19 April 2026 with a rebrand and refactor of an earlier private repository, so that date is the start of this codebase, not the start of the idea.

## Tenant model

Noxivo's core operating model is explicit: Platform → Agency → Tenant / client workspace. The dashboard makes that hierarchy visible, while the repository carries the active tenant context through memberships, request and session context, service queries, worker payloads, scoped models, credentials, conversations, workflows, sessions, and integrations.

## Durable workflow execution

The workflow editor and the execution model are separate concerns. A graph is compiled into a DAG before workers run it, with validation for trigger structure, edges, branches, cycles, delays, and scoped plugin references. Persisted workflow runs and per-node events provide a record around execution. Delays resume through queue-backed jobs with deterministic job ids, and handing a conversation to a human cancels the pending continuation. Delivery is at least once, not exactly once, and it relies on Redis persistence with a one-second flush.

## Live inbox architecture

The inbox is database-first. Conversation and message records remain the source of truth, with agency and tenant scope carried into assignment, status, unread state, customer context, and synchronization. Live updates can move through Redis pub/sub to SSE clients, with a local subscriber fallback when Redis is unavailable.

  title="Database-first live updates"
  subtitle="State and events have different jobs"
  problem="A live event stream is fast for interface updates but is a fragile source of truth for conversations, assignments, and unread state."
  decision="Persist scoped conversation and message state first, then fan out tenant-scoped events through Redis pub/sub and SSE, with a local subscriber fallback."
  result="The interface can stay current without making the event stream responsible for durable product state."

## Developer platform

The dashboard is paired with a developer surface rather than treated as the only integration path. The repository evidence includes tenant-scoped public API operations, bearer or API-key authentication, plan-based rate limiting, webhook subscriptions with signed delivery and a server-side request guard, and SDK package directories for Node, Python, PHP, and Laravel. The SDKs are not published to a package registry yet. Docusaurus documentation and an n8n-oriented package or guide extend the integration story.
